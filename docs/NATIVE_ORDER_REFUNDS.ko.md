# 네이티브 주문 내역·미개봉 환불 — 개발 연결

2026-09-16. 앱 기준 6f2b872, 서버 계약 기준 9be81a0(런타임 38cacbdd). 체크리스트 10번의 부분 작업이다. 실제 서버·원본 DB·PG·출시 게이트는 변경하지 않는다.

## 실제 연결 경로

마이 → 주문·환불 내역 → GET /transactions/capabilities 및 /transactions/orders?page=N&limit=20 → GET /orders/:id.
환불 내역은 GET /order-refunds/capabilities, /order-refunds?page=N&limit=20.
미개봉 선택 → POST /orders/:id/refund-quote → 원결제수단/금액/캡슐 확인·동의 → 보안 저장 → POST /orders/:id/refunds(Idempotency-Key).
응답 유실/재시작 → GET /order-refunds/by-request/:key. 조회는 환불을 실행하지 않는다.

구매 완료/일부 환불/전체 환불과 미개봉/개봉/환불 처리 중/환불 완료를 별도 모델로 처리한다. 기존 GP 구매 Receipt의 좁은 계약을 넓혀 구매 완료 검증을 약하게 만들지 않는다.

## 안전 규칙

- 계정·서버별 동일 요청번호/본문을 안전 저장소에 먼저 기록한다. 비밀번호·토큰·카드정보는 기록하지 않는다. 사유는 사용자가 입력한 내용으로 해당 보안 저장소에만 저장한다.
- 토큰을 캡처한 세션과 현재 로그인 세대를 함께 검사한다. 비동기 토큰 읽기 후/응답 후 세대를 재확인하고 리다이렉트를 따르지 않는다.
- 수량/통화/원가격/캡슐 목록/정책/기한을 서버 응답과 대조한다. 숫자·상태·날짜가 잘못되면 빈 내역이나 0원으로 대체하지 않는다.
- PROCESSING/UNKNOWN은 조회만 허용한다. APPROVED 또는 명시적인 서버 기록 없음에 대해서만 사용자 확인 후 같은 키/본문으로 재개한다. 새 결제사 취소 여부는 기존 서버 멱등 구현에 의존한다.
- 최초 요청의 명확한 거절을 직접 수신하고 서버 요청 장부도 없음을 확인한 경우만 해당 로컬 요청을 해제한다. 이전 불명확 요청을 재시도하다 거절되면 기록을 유지한다. HTTP 오류만으로 중복 실행 가능성을 무시하지 않는다.
- 성공 응답도 서버에서 다시 확인하고 사용자가 완료를 확인할 때까지 로컬 요청을 보관한다. 저장소 삭제 실패를 환불 실패로 판단해 새 환불하지 않는다.
- 새 선택·견적 재조회 시 기존 금액/동의를 무효화한다. 로그인 변경 시 거래 자료를 지운다.
- 과거 환불 정책이 비어 있으면 자동 환불 미확인과 고객지원 경로를 표시한다. 고객의 법적 환불권이 없다는 결론을 표시하지 않는다. 7영업일 등 값은 현재 서버 계약이며 법률 적합성 승인이 아니다.

## 실행과 검증 범위

신규 환불 실행은 기존 거래와 같은 개발 전용 정책이다. ENABLE_ORDER_REFUND_PREVIEW=true를 명시한 비release 앱과 서버가 모두 허용한 경우만 신청할 수 있다. 이번 작업에서 실제 사용자용 빌드 플래그를 활성화하지 않는다. release 빌드에서는 여전히 실행되지 않으며 내역 조회만 가능하다.

합성 HTTP/메모리 저장소의 저장·재시도·경쟁·모델 검사와 Flutter 화면 검사로 계약을 확인한다. 메모리 저장소 시험을 실제 기기의 Keychain/Keystore 지속성 검수나 PG 실승인으로 표현하지 않는다. 카드의 승인/취소/정산, 원본 계정, 폰에서의 전체 거래, 관리자 주문 동기화, 반품/개봉 후 분쟁, 최종 환불 정책은 별도다.

완료 점수는 올리지 않는다. 10번에는 이메일 복구/탈퇴 등 남은 계정 계약, 실제 카드 결제 흐름, 전체 모바일 연결 전수 검수가 남아 있다. 기존 44/100 체크리스트를 유지한다.
